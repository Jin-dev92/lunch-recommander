# 위치 기반 점심 추천 웹앱 설계 스펙

## 1. 프로젝트 개요

이 프로젝트는 사용자의 현재 위치를 기준으로 주변 음식점 한 곳을 추천하는 웹앱입니다. 주변 음식점과 구글 평점은 Google Places API에서 조회합니다. 각 음식점에는 사용자의 개인 평점, 음식 카테고리 기호, 같은 그룹에 속한 사용자들의 평균 평점, 구글 평점, 거리 보정을 반영한 가중치를 부여합니다.

**가중 랜덤**은 점수가 높은 후보일수록 선택될 확률이 높아지는 무작위 추출 방식입니다. 점수가 가장 높은 음식점을 항상 고정적으로 보여 주지 않기 때문에 사용자 취향을 반영하면서도 다양한 음식점을 발견할 수 있습니다.

## 2. 핵심 결정

### 2.1 서비스 형태와 평점 출처

- 서비스 형태는 웹앱입니다.
- 외부 음식점 평점은 Google Places API에서 가져옵니다. Google Places API는 `rating`과 리뷰 수를 제공하지만, 카카오와 네이버는 공식 API로 평점을 제공하지 않으므로 사용하지 않습니다.
- 사용자는 로그인해야 하며, 사용자 데이터는 `localStorage`가 아니라 Supabase 데이터베이스에 저장합니다. 이를 통해 여러 기기에서 동일한 데이터에 접근하고 서버 측 접근 제어를 적용할 수 있습니다.

### 2.2 평점 모델과 그룹 경계

평점 모델은 개인 평점과 그룹 평균을 함께 표시하고 추천에 모두 반영하는 하이브리드 방식입니다.

그룹은 초대코드로 가입합니다. 같은 초대코드로 연결된 그룹 구성원끼리만 서로의 평점을 볼 수 있습니다. 이 경계는 임의 가입으로 인한 데이터 오염을 막고, 허가되지 않은 사용자가 Google Places API를 반복 호출하는 위험을 줄이기 위해 필요합니다.

## 3. 기술 스택

### 3.1 프론트엔드

- Next.js: 지도 화면, 사용자 인터페이스, 페이지 라우팅을 담당합니다.
- Vercel: Next.js 웹앱을 배포합니다.

### 3.2 백엔드

백엔드는 Supabase 하나로 구성합니다.

- Supabase Auth: 사용자 로그인과 인증을 담당합니다.
- Supabase Postgres: 사용자, 그룹, 음식점, 평점, 기호, 사용량 데이터를 저장합니다.
- RLS: 데이터베이스의 각 행에 대해 현재 사용자가 읽거나 쓸 수 있는 범위를 제한하는 PostgreSQL 보안 기능입니다.
- Edge Function: 브라우저 대신 외부 API를 호출하고 인증, 사용량 제한, 캐시 처리를 수행하는 서버 측 함수입니다.

## 4. 전체 아키텍처

### 4.1 브라우저의 역할

Next.js 브라우저 애플리케이션은 다음 작업을 담당합니다.

- Maps JavaScript API로 구글 지도를 렌더링합니다.
- Supabase Auth로 사용자를 로그인시킵니다.
- Supabase JavaScript 클라이언트로 개인 평점과 카테고리 기호를 읽고 씁니다. 각 요청은 RLS로 보호됩니다.

지도 렌더링에는 HTTP referrer 제한을 적용한 별도 API 키를 사용합니다. 이 키는 허용된 웹사이트에서만 사용할 수 있도록 제한하므로 브라우저에 노출될 수 있습니다.

### 4.2 Supabase의 역할

Supabase는 다음 작업을 담당합니다.

- Auth로 로그인 상태와 사용자 신원을 확인합니다.
- Postgres와 RLS로 데이터를 저장하고 사용자별 접근 범위를 제한합니다.
- `nearby` Edge Function으로 Google Places API 요청을 중계합니다.

Google Places API를 이용한 주변 음식점 검색과 평점 조회는 반드시 Edge Function을 거쳐야 합니다. 브라우저에서 Google Places API를 직접 호출해서는 안 됩니다.

## 5. 보안 원칙

### 5.1 Google API 키 분리

Google API 키는 용도에 따라 다음 두 개로 분리합니다.

- 지도 렌더링 키: HTTP referrer 제한을 적용하며 브라우저 노출을 허용합니다.
- Places 검색 키: Edge Function의 서버 환경에만 저장하며 브라우저에 절대 노출하지 않습니다.

### 5.2 서버 측 사용량 제한

주변 음식점 검색과 평점 조회에는 Edge Function에서 사용자 ID와 IP를 함께 사용하는 이중 사용량 제한을 적용합니다. 프론트엔드에만 사용량 제한을 두지 않습니다. 사용자 ID와 IP를 함께 검사하면 다른 계정으로 로그인하거나 IP를 바꾸는 한 가지 방법만으로 제한을 우회하기 어려워집니다.

**Rate limit**은 일정 시간 동안 허용할 요청 횟수를 제한하여 남용과 과도한 비용을 방지하는 방식입니다.

### 5.3 운영 환경 설정과 요금 방어

키 탈취나 애플리케이션 버그로 인한 과금을 막기 위해 Google Cloud 운영 환경에서 다음을 설정합니다. 이 항목들은 코드가 아니라 Google Cloud 콘솔 또는 `gcloud` CLI로 수행합니다.

- **미사용 API 비활성화**: 이 프로젝트가 쓰는 API(Maps JavaScript, Places)만 활성화하고, Generative Language(Gemini)·Vertex AI 등 사용하지 않는 API는 모두 비활성화합니다. 비활성화한 API는 키가 탈취돼도 호출·과금이 불가능합니다.
- **API 키 제한**: 각 키에 "호출 가능한 API"를 화이트리스트로 제한합니다(예: 렌더링 키는 Maps JavaScript만, 서버 키는 Places만). 애플리케이션 제한도 함께 걸어 렌더링 키는 HTTP referrer, 서버 키는 IP로 제한합니다.
- **할당량(Quota) 상한**: 사용하는 각 API의 일일 할당량을 월 무료 한도 안으로 낮춰 설정합니다. 상한을 넘는 요청은 거부되어 과금되지 않으므로, 실질적인 하드 캡 역할을 합니다.
- **Budget Alert**: 비용이 기준에 도달하면 알림을 보내는 예산 기능입니다. 자동 차단이 아니라 알림이므로, 위 할당량 상한과 병행합니다.

Edge Function의 서버 측 rate limit(user_id + IP)이 1차 방어, GCP 할당량 상한이 최종 방어로 이중 구성됩니다.

## 6. 데이터 모델

### 6.1 `profiles`

사용자 표시 정보를 저장합니다.

| 필드           | 설명                                   |
| -------------- | -------------------------------------- |
| `id`           | `auth.uid`와 같은 사용자 식별자입니다. |
| `display_name` | 화면에 표시할 사용자 이름입니다.       |

### 6.2 `groups`

초대코드 기반 그룹을 저장합니다.

| 필드          | 설명                                 |
| ------------- | ------------------------------------ |
| `id`          | 그룹 식별자입니다.                   |
| `name`        | 그룹 이름입니다.                     |
| `invite_code` | 중복을 허용하지 않는 초대코드입니다. |
| `created_by`  | 그룹을 만든 사용자입니다.            |

### 6.3 `group_members`

사용자와 그룹의 소속 관계를 저장합니다.

| 필드       | 설명                              |
| ---------- | --------------------------------- |
| `group_id` | 그룹 식별자입니다.                |
| `user_id`  | 사용자 식별자입니다.              |
| `role`     | `admin` 또는 `member` 역할입니다. |

기본 키는 `group_id`와 `user_id`의 조합입니다.

### 6.4 `restaurants`

Google Places API에서 받은 음식점 결과를 공용 캐시로 저장합니다. 같은 음식점 정보를 반복 호출하지 않도록 하여 API 사용량과 비용을 줄입니다.

| 필드                   | 설명                               |
| ---------------------- | ---------------------------------- |
| `place_id`             | 구글이 부여한 음식점 식별자입니다. |
| `name`                 | 음식점 이름입니다.                 |
| `category`             | 음식 카테고리입니다.               |
| `lat`                  | 위도입니다.                        |
| `lng`                  | 경도입니다.                        |
| `google_rating`        | 구글 평점입니다.                   |
| `google_ratings_total` | 구글 리뷰 수입니다.                |
| `fetched_at`           | 구글에서 정보를 가져온 시각입니다. |

### 6.5 `ratings`

사용자가 음식점에 부여한 개인 평점을 저장합니다.

| 필드            | 설명                                                                                                                                         |
| --------------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| `user_id`       | 평점을 남긴 사용자입니다.                                                                                                                    |
| `place_id`      | 대상 음식점의 구글 식별자입니다.                                                                                                             |
| `score`         | 개인 평점입니다. 기본 범위는 1~5이며, 영구적으로 추천에서 제외할 때 0점을 사용합니다.                                                        |
| `snoozed_until` | 일시적으로 추천에서 제외할 기한입니다. 이 시각이 지나면 별도 처리 없이 자동으로 다시 추천 후보가 됩니다. 비어 있으면 스누즈 상태가 아닙니다. |

`user_id`와 `place_id`의 조합은 중복을 허용하지 않습니다.

### 6.6 `category_prefs`

사용자의 음식 카테고리별 기호를 저장합니다.

| 필드       | 설명                                 |
| ---------- | ------------------------------------ |
| `user_id`  | 사용자 식별자입니다.                 |
| `category` | 음식 카테고리입니다.                 |
| `weight`   | 해당 카테고리를 선호하는 정도입니다. |

`user_id`와 `category`의 조합은 중복을 허용하지 않습니다.

### 6.7 `api_usage`

사용량 제한 계산만을 위한 별도 테이블입니다.

| 필드           | 설명                                              |
| -------------- | ------------------------------------------------- |
| `user_id`      | 요청한 사용자입니다.                              |
| `ip`           | 요청한 IP 주소입니다.                             |
| `window_start` | 요청 횟수를 집계하는 시간 구간의 시작 시각입니다. |
| `count`        | 해당 시간 구간의 요청 횟수입니다.                 |

`api_usage`는 일반 사용자 데이터나 민감 데이터와 섞지 않습니다. 사용량 데이터와 다른 성격의 데이터를 분리하면 접근 정책을 더 좁게 적용하고 사용자가 자신의 제한 값을 조작하는 경로를 차단할 수 있습니다.

## 7. RLS 정책

**RLS(Row Level Security)**는 로그인한 사용자와 행의 관계를 검사하여 테이블의 개별 행에 대한 읽기와 쓰기를 제한하는 기능입니다. 모든 테이블은 RLS 활성화 여부를 확인하고, 아래 정책을 적용합니다.

| 테이블           | 읽기 정책                                                       | 쓰기 정책                                                                         |
| ---------------- | --------------------------------------------------------------- | --------------------------------------------------------------------------------- |
| `profiles`       | 본인과 본인과 그룹을 공유하는 사용자의 정보만 읽을 수 있습니다. | 본인 정보만 쓸 수 있습니다.                                                       |
| `groups`         | 그룹 멤버만 해당 그룹을 읽을 수 있습니다.                       | 그룹 생성자인 `admin`만 쓸 수 있습니다.                                           |
| `group_members`  | 같은 그룹에 속한 멤버만 읽을 수 있습니다.                       | 직접 `INSERT`할 수 없으며, 초대코드를 검증하는 RPC를 통해서만 가입할 수 있습니다. |
| `restaurants`    | 로그인한 사용자는 모두 읽을 수 있습니다.                        | `service_role`을 사용하는 Edge Function만 쓸 수 있습니다.                         |
| `ratings`        | 본인과 본인과 그룹을 공유하는 사용자의 평점만 읽을 수 있습니다. | `user_id = auth.uid()`인 본인 평점만 쓸 수 있습니다.                              |
| `category_prefs` | 본인 데이터만 읽을 수 있습니다.                                 | 본인 데이터만 쓸 수 있습니다.                                                     |
| `api_usage`      | 사용자 접근을 완전히 차단합니다.                                | `service_role`을 사용하는 Edge Function만 조작할 수 있습니다.                     |

**RPC(Remote Procedure Call)**는 클라이언트가 데이터베이스에 정의된 함수를 호출하는 방식입니다. 그룹 가입 RPC는 초대코드를 검증한 뒤에만 멤버십을 생성합니다.

`service_role`은 RLS를 우회할 수 있는 Supabase 서버 전용 권한입니다. 따라서 브라우저에 노출하지 않고 Edge Function 내부에서만 사용합니다.

### 7.1 RLS 우회 경로 검토

- `ratings` 읽기 정책은 `group_members` 자기조인으로 공유 그룹 여부를 판단합니다. 정책 범위가 느슨하면 전체 사용자의 평점이 노출될 수 있으므로, 현재 사용자와 최소 한 그룹이라도 함께 속한 사용자의 평점만 읽을 수 있도록 제한합니다.
- `group_members`에 직접 `INSERT`를 허용하면 사용자가 임의의 `group_id`를 지정해 무단 가입할 수 있습니다. 직접 삽입은 막고 초대코드 검증 RPC를 통해서만 가입시킵니다.
- `api_usage`는 사용자가 직접 읽거나 조작할 수 없도록 완전히 차단하고 Edge Function만 접근하도록 합니다.

이 정책들을 구현한 뒤에는 다른 사용자 데이터에 접근할 수 있는 우회 경로가 남아 있는지 다시 검토해야 합니다. 특히 그룹 관계를 이용해 그룹 외부 평점이 노출되지 않는지, 초대코드 검증 없이 멤버십을 만들 수 없는지, 사용량 집계 값을 사용자가 변경할 수 없는지 확인합니다.

데이터 모델 구현 전에는 민감 데이터와 사용량 데이터가 같은 테이블에 혼재하지 않는지 사람이 직접 확인해야 합니다.

## 8. 추천 로직

### 8.1 처리 흐름

1. 브라우저의 Geolocation으로 현재 위치를 얻고 검색 반경을 선택합니다. 반경 예시는 500m 또는 1km입니다.
2. `nearby` Edge Function이 Google Places API를 통해 선택한 반경 안의 음식점 후보와 구글 평점을 조회합니다.
3. 각 후보에 가중치를 부여하고 가중 랜덤으로 한 곳을 추천합니다. 점수가 가장 높은 한 곳을 항상 고정적으로 선택하지는 않습니다.

**Geolocation**은 사용자의 동의를 받아 브라우저가 현재 위치의 위도와 경도를 제공하는 기능입니다.

### 8.2 가중치 공식

```text
weight = 카테고리기호 × 개인평점 × 그룹평균 × 구글평점 × 거리보정
```

각 요소는 다음과 같이 계산합니다.

- 카테고리 기호: `category_prefs.weight`를 사용합니다. 예를 들어 한식은 1.5, 일식은 0.5로 둘 수 있으며, 설정하지 않은 카테고리는 1.0입니다.
- 개인 평점: 내 `ratings.score`를 1~5 범위에서 정규화합니다. 0점은 가고 싶지 않은 음식점을 뜻하며 추천 후보에서 제외합니다.
- 그룹 평균: 현재 사용자와 그룹을 공유하는 사용자들의 평균 평점을 사용합니다. 평점이 없으면 중립값 1.0을 사용합니다.
- 구글 평점: `google_rating`을 정규화합니다. 리뷰 수가 적으면 신뢰도를 낮게 반영합니다.
- 거리 보정: 가까운 음식점일수록 가중치를 소폭 높입니다.

**정규화**는 서로 다른 값의 범위와 단위를 추천 공식에서 비교하고 곱할 수 있도록 공통 기준으로 바꾸는 과정입니다.

### 8.3 결측값 처리

아직 개인 평점이나 그룹 평점이 없는 새 음식점은 해당 요소를 중립값 1.0으로 둡니다. 평점이 없다는 이유로 새 음식점을 후보에서 제외하지 않으므로 사용자는 이전에 평가하지 않은 장소도 발견할 수 있습니다. 구글 평점만 있는 음식점도 추천 후보가 됩니다.

### 8.4 일시 스누즈

좋아하는 음식점이라도 한동안 질려서 가고 싶지 않을 때 추천에서 잠시 빼는 기능입니다. 개인 평점을 0점으로 낮추는 영구 제외와 달리, 평점은 그대로 유지하고 정해진 기간 동안만 추천 후보에서 제외합니다. 따라서 스누즈가 끝나면 원래의 선호도가 그대로 되살아납니다.

- 사용자가 해당 음식점에서 "1주간 그만 보기"를 선택하면 `ratings.snoozed_until`을 현재 시각 기준 7일 뒤로 설정합니다.
- 추천 후보를 조회할 때 `snoozed_until`이 현재 시각보다 미래인 음식점은 후보에서 제외합니다. 기한이 지난 음식점은 별도 배치 작업 없이 조회 조건에서 자동으로 다시 후보에 포함됩니다.
- 스누즈 기간은 1주로 고정하며 버튼 하나로 조작합니다. 영구 제외(0점)와 일시 스누즈는 서로 독립적인 조작입니다.

### 8.5 가중치 튜닝

각 요소가 결과에 미치는 강도를 조절하는 지수는 상수로 분리합니다. 초기 값은 휴리스틱이므로 실제 사용 결과를 확인하며 조정합니다.

**휴리스틱**은 완전히 증명된 최적값이 아니라 경험과 관찰을 바탕으로 정한 실용적인 초기 기준입니다.

구현 시 해당 상수에는 다음 형식의 주석을 표시합니다.

```text
ponytail: 휴리스틱 가중치, 써보고 조정
```

## 9. `nearby` Edge Function

`nearby` Edge Function은 다음 순서로 요청을 처리합니다.

1. Supabase JWT를 확인하여 사용자를 인증하고 위치와 반경을 입력받습니다.
2. `api_usage`에서 사용자 ID와 IP 조합의 시간 구간별 요청 횟수를 검사합니다. 한도를 넘으면 HTTP 429 응답을 반환합니다.
3. 최근에 조회한 좌표 또는 `place_id`에 해당하는 데이터가 있으면 `restaurants` 캐시를 우선 사용합니다. 캐시에 없을 때만 Google Places API를 호출합니다.
4. 서버 환경에 숨긴 Places 검색 키로 Google Places API를 호출하고, 결과를 `restaurants`에 upsert한 뒤 반환합니다.

**JWT(JSON Web Token)**는 로그인한 사용자의 신원을 서버가 검증할 수 있도록 서명된 인증 정보를 담는 토큰입니다.

**upsert**는 같은 식별자의 데이터가 없으면 새로 추가하고, 이미 있으면 갱신하는 저장 방식입니다.

사용자 ID와 IP를 함께 제한하므로 로그인 계정 변경과 IP 변경 중 한 가지 방법만으로는 제한을 우회할 수 없습니다.

사용량 제한 구현부에는 다음 취지의 주석을 반드시 남깁니다.

```text
요금폭탄 주의: 스팸 요청이 구글 API 과금으로 직결
```

## 10. 테스트와 검증

검증 프레임워크는 최소한으로 사용하고, 비용과 보안에 직접 영향을 주는 핵심 로직만 확인합니다.

### 10.1 추천 로직 단위 테스트

가중치 계산과 가중 랜덤을 외부 상태에 의존하지 않는 순수 함수로 분리하여 다음 동작을 확인합니다.

- 개인 평점이 0점인 음식점은 추천 후보에서 제외됩니다.
- `snoozed_until`이 미래인 음식점은 추천 후보에서 제외되고, 기한이 지나면 다시 후보에 포함됩니다.
- 충분한 횟수로 추출했을 때 가중치가 높은 음식점 쪽으로 선택 분포가 편향됩니다.

**순수 함수**는 같은 입력에 항상 같은 계산 결과를 반환하고 함수 밖의 상태를 변경하지 않는 함수입니다.

### 10.2 RLS SQL 테스트

그룹을 공유하지 않는 다른 사용자로 접속했을 때 타인의 `ratings`를 읽을 수 없는지 SQL 테스트 한 개로 확인합니다.

### 10.3 사용량 제한 테스트

`nearby` Edge Function의 허용 요청 횟수를 초과했을 때 HTTP 429 응답이 반환되는지 확인합니다.

## 11. 향후 확장

초기 버전은 초대코드 기반 그룹 공유 모델로 시작합니다. 데이터 저장 접근은 저장소 모듈 한 곳으로 격리합니다. 향후 그룹 또는 공유 요구가 바뀌더라도 저장 방식을 수정해야 하는 지점을 최소화하기 위한 구조입니다.

## 12. 리서치 근거

- Google Places API는 `rating`과 `user_ratings_total`을 제공합니다.
- Google Maps Platform은 2025년 3월 과금 체계 개편으로 월 200달러 통합 크레딧을 폐지하고 SKU별 월 무료 호출 수를 적용합니다. Pro 등급은 약 월 5,000건의 무료 호출 범위를 제공합니다. 개인 또는 소규모 서비스는 사실상 무료 범위에서 운영할 수 있지만 카드 등록과 Budget Alert 설정이 필요합니다.
- 카카오와 네이버는 공식 API로 평점을 제공하지 않습니다. 평점을 스크래핑하는 방식은 약관에 위배되므로 사용하지 않습니다.
