# 프론트엔드 데이터 레이어 리팩토링 설계

**작성일:** 2026-07-23
**대상:** `app/`, `components/`, `lib/`, `middleware.ts`
**근거 규칙:** 프로젝트 루트 `CLAUDE.md` (Next.js / Frontend / TypeScript / 매직 스트링 규칙)

---

## 1. 배경

이 프로젝트의 프론트엔드는 화면 컴포넌트가 데이터 접근까지 함께 담당하는 구조였습니다.
컴포넌트가 Supabase 클라이언트를 직접 import해 테이블명과 컬럼명을 문자열로 적고,
응답의 `error` 필드를 각자 분기해 화면 문구를 만들었습니다.

이 구조에는 세 가지 문제가 있습니다.

1. **동일한 문자열이 여러 파일에 흩어집니다.** 세션 쿠키 이름 `sb-session`은 로그인 화면,
   홈 화면, 미들웨어 세 곳에 각각 하드코딩되어 있었습니다. 한 곳만 바꾸면 인증이 조용히 깨집니다.
2. **타입이 경계에서 끊깁니다.** Supabase 응답에 제네릭을 주지 않으면 반환값이 `any`가 되고,
   그 값이 그대로 화면까지 흘러 컴파일러가 오타를 잡지 못합니다.
3. **서버 상태를 컴포넌트의 `useState`로 관리합니다.** 로딩 여부를 나타내는 boolean을
   손으로 켜고 끄는 코드가 화면마다 반복되고, 저장 성공 후 관련 데이터를 다시 읽는 지점이
   명시되지 않습니다.

`CLAUDE.md`는 이 세 가지를 각각 "매직 스트링 단일 출처", "API 함수 제네릭 타입 명시 필수",
"서버 상태는 React Query" 규칙으로 이미 금지하고 있습니다. 이번 작업은 규칙을 코드에 반영합니다.

## 2. 목표와 비목표

**목표**

- 컴포넌트에서 데이터 접근 코드를 제거하고 전용 레이어로 옮깁니다.
- 반복되는 식별자와 사용자 노출 문구를 각각 단일 출처 파일로 모읍니다.
- 서버 상태를 React Query가 관리하게 하고, 폼 상태를 React Hook Form이 관리하게 합니다.

**비목표**

- 화면 디자인과 CSS는 바꾸지 않습니다. 시각 판단이 필요한 작업은 별도 레인의 몫입니다.
- 추천 알고리즘(`lib/recommend.ts`의 점수 계산과 가중 추첨)은 그대로 둡니다.
- 데이터베이스 스키마와 RLS 정책은 건드리지 않습니다.

## 3. 레이어 구조

용어를 먼저 정리합니다.

- **API 함수(API function)**: 외부 시스템과 실제로 통신하는 함수입니다. React를 모릅니다.
- **쿼리 훅(query hook)**: 읽기 요청을 React 컴포넌트가 쓸 수 있는 형태로 감싼 훅입니다.
- **뮤테이션 훅(mutation hook)**: 쓰기 요청을 감싼 훅입니다. 성공 시 캐시 무효화를 담당합니다.

레이어는 아래 방향으로만 의존합니다. 화살표를 거스르는 import는 없습니다.

```
컴포넌트 (app/, components/)
    │  훅만 호출한다
    ▼
훅 (lib/hooks/queries, lib/hooks/mutations)
    │  API 함수만 호출한다
    ▼
API 함수 (lib/api/)
    │
    ├──▶ supabaseClient  … 데이터베이스 질의와 인증
    └──▶ axiosInstance   … 자체 HTTP 엔드포인트(Edge Function)
```

디렉터리는 `CLAUDE.md`의 "API 레이어 4파일 세트"를 이 프로젝트의 레이아웃(`src/` 없이 루트
`lib/` 사용)에 맞춰 옮긴 것입니다.

```
lib/api/{도메인}.ts                          API 함수
lib/types/api/{도메인}.types.ts              타입 정의
lib/hooks/queries/use{도메인}Queries.ts      쿼리 훅
lib/hooks/mutations/use{도메인}Mutations.ts  뮤테이션 훅
```

각 디렉터리에는 `index.ts` 배럴 파일을 둡니다.

## 4. 주요 설계 결정

### 4.1 axios는 Edge Function 호출에만 씁니다

axios는 HTTP 요청을 보내는 라이브러리입니다. 이 프로젝트의 데이터 접근은 두 종류로 나뉩니다.

| 대상                                                     | 성격                                    | 사용 도구     |
| -------------------------------------------------------- | --------------------------------------- | ------------- |
| `ratings`, `category_prefs` 테이블, RPC, 로그인·로그아웃 | Supabase SDK가 RLS와 토큰 갱신까지 처리 | `supabase-js` |
| `nearby` Edge Function                                   | 우리가 직접 만든 HTTP 엔드포인트        | `axios`       |

전자를 axios로 바꾸면 Supabase REST 규약과 JWT(JSON Web Token, 로그인 사용자를 증명하는
서명된 문자열) 갱신 로직을 직접 구현해야 하고, 이는 보안 관련 코드를 손으로 다시 짜는 일입니다.
따라서 axios는 후자에만 적용했습니다.

`lib/axiosInstance.ts`는 두 가지를 인터셉터(interceptor, 요청과 응답을 가로채 가공하는 훅)로 처리합니다.

1. **요청 인터셉터**: 매 요청 직전에 현재 세션의 액세스 토큰을 읽어 `Authorization` 헤더에 붙입니다.
   토큰은 세션 갱신마다 바뀌므로 모듈 로드 시점에 캐싱하지 않습니다.
2. **응답 인터셉터**: Edge Function이 실패 시 돌려주는 `{ error: "문구" }`를 `Error.message`로
   승격시킵니다. 화면은 서버가 준 한국어 문구를 그대로 쓸 수 있습니다.

### 4.2 Supabase의 `{ data, error }`를 예외로 승격시킵니다

`supabase-js`는 실패해도 예외를 던지지 않고 `{ data, error }` 형태의 객체를 돌려줍니다.
호출부가 매번 `if (error)`를 적으면 분기가 코드 전체에 번집니다.

`lib/api/unwrap.ts`가 이 변환을 한 곳에서 담당합니다.

- `unwrap(result)` — 응답 데이터가 필요한 읽기에 씁니다. `error`가 있으면 던지고, 없으면 `data`를 반환합니다.
- `assertNoError(result)` — 성공 여부만 확인하면 되는 쓰기에 씁니다. 응답 `data`의 형태에 묶이지 않습니다.

두 함수로 나눈 이유는 타입 때문입니다. `signInWithPassword`처럼 성공과 실패에서
`data`의 타입이 서로 다른 유니온을 반환하는 API는 단일 제네릭으로 좁힐 수 없습니다.

결과적으로 화면은 예외 하나만 보면 되고, React Query가 그 예외를 `error` 상태로 바꿔 줍니다.

### 4.3 추천 데이터는 버튼을 눌렀을 때만 가져옵니다

`nearby` Edge Function은 캐시가 없을 때 Google Places API를 호출합니다. 이 호출은 과금 대상이며,
서버에는 사용자 ID와 IP 기준 레이트 리밋(rate limit, 일정 시간 안의 요청 횟수 제한)이 걸려 있습니다.

React Query의 `useQuery`는 기본적으로 마운트 시점에 자동으로 요청을 보냅니다. 그대로 두면
사용자가 추천을 요청하지 않았는데도 화면에 들어오기만 하면 과금이 발생합니다.

따라서 `useRecommendationData`는 `enabled: false`로 선언하고, 컴포넌트가 추천 버튼 클릭 시
`refetch()`로만 호출합니다. 재시도(`retry`)도 끕니다. 실패한 요청을 자동으로 세 번 더 보내는
기본 동작은 레이트 리밋 소진으로 이어지기 때문입니다.

추첨 결과는 누를 때마다 달라져야 하므로 캐시된 값을 재사용하지 않고 매번 `refetch()`합니다.

### 4.4 무효화 대상은 `recommend` 도메인입니다

`CLAUDE.md`는 뮤테이션 훅의 `onSuccess`에서 자기 도메인의 쿼리를 무효화하도록 규정합니다.
이 프로젝트에서 평점(`ratings`), 카테고리 기호(`category_prefs`), 그룹(`groups`)은
자체 조회 화면이 없고, 추천 후보의 점수를 계산하는 입력으로만 쓰입니다.

그래서 이 세 도메인의 뮤테이션은 `recommendQueryKeys.all`을 무효화합니다. 무효화 대상이 없는
쿼리 키를 형식적으로 만들기보다, 실제로 영향을 받는 데이터를 가리키는 편이 정확합니다.

같은 이유로 조회가 없는 도메인에는 `use{도메인}Queries.ts` 파일을 만들지 않았습니다.
4파일 세트 규칙에서 벗어나는 유일한 지점이며, 빈 파일을 남기지 않기 위한 선택입니다.

### 4.5 UI 후처리는 소비 컴포넌트가 맡습니다

`CLAUDE.md`는 뮤테이션 훅의 `onSuccess`에 토스트나 알림을 넣는 것을 금지합니다.
훅은 캐시 무효화만 담당하고, 화면 이동이나 쿠키 조작 같은 후처리는 컴포넌트가 처리합니다.

한 가지 주의점이 있습니다. `useMutation({ onSuccess, ...options })` 형태에서 소비 컴포넌트가
훅 옵션으로 `onSuccess`를 넘기면 훅이 정의한 무효화가 **덮어써집니다.** 그래서 소비 컴포넌트는
훅 옵션이 아니라 `mutate(변수, { onSuccess })`로 콜백을 넘깁니다. 이렇게 하면 React Query가
두 콜백을 모두 실행하므로 무효화가 유실되지 않습니다.

## 5. 상수와 문구의 분리

`CLAUDE.md`는 식별자와 사용자 노출 문구를 서로 다른 파일에 두도록 규정합니다.

| 파일               | 담는 것                | 예                                                        |
| ------------------ | ---------------------- | --------------------------------------------------------- |
| `lib/constants.ts` | 결합용 식별자          | `SESSION_COOKIE`, `ROUTES`, `TABLE`, `ON_CONFLICT`, `RPC` |
| `lib/messages.ts`  | 사용자에게 보이는 문구 | `MESSAGES.LOGIN_REQUIRED`                                 |

값이 정해진 닫힌 집합은 `as const` 객체로 선언합니다. `enum`은 사용하지 않습니다.
번들러가 사이드 이펙트 없음을 판단하지 못해 트리 셰이킹에서 제외될 수 있기 때문입니다.

`lib/messages.ts`에는 `errorMessage(error: unknown): string` 헬퍼도 함께 둡니다.
`catch`로 받은 값은 타입이 `unknown`이라 그대로 화면에 넣을 수 없으므로, 이 헬퍼가
`Error`면 `message`를, 아니면 기본 문구를 돌려줍니다.

## 6. 검증 기준

| 항목   | 명령                   | 기준                 |
| ------ | ---------------------- | -------------------- |
| 타입   | `npm run typecheck`    | 오류 0               |
| 린트   | `npm run lint`         | 경고 0               |
| 테스트 | `npm test`             | 전체 통과            |
| 포맷   | `npm run format:check` | 전체 통과            |
| 빌드   | `npm run build`        | 성공 (환경변수 필요) |

동작 보존은 기존 테스트가 담보합니다. 테스트는 어설션(assertion, 기대값 검증)을 바꾸지 않고,
React Query Provider 래핑과 모킹 대상 변경만 반영합니다. 유일한 의도적 동작 변경은
4.3의 "마운트 시 자동 호출 안 함"이며, 이는 기존에도 버튼 클릭으로만 호출되던 동작과 동일합니다.

## 7. 남는 과제

- `npm audit`에 `postcss`와 `sharp` 취약점이 남아 있습니다. `next`의 전이 의존성이며
  `npm audit fix --force`는 `next`를 9.x로 내리므로 적용하지 않았습니다.
- `middleware.ts`는 여전히 쿠키 존재 여부만 확인합니다. 서버에서 JWT 서명까지 검증하려면
  `@supabase/ssr` 도입이 필요하며, 이번 범위에 포함하지 않았습니다.
