# 관리자 승인 기반 회원가입 설계 스펙

## 1. 개요

위치 기반 점심 추천 웹앱에는 현재 이메일과 비밀번호로 로그인하는 `signInWithPassword` 흐름만 있고, 새로운 사용자가 회원가입을 요청할 수 있는 경로는 없습니다.

이 문서는 아무나 계정을 만들 수 없도록 관리자 승인 기반 회원가입을 추가하는 설계를 정의합니다. 방문자가 이메일 주소로 가입을 요청하면 관리자에게 알림이 전송됩니다. 관리자가 요청을 확인하고 승인하면 방문자에게 비밀번호 설정 링크가 전달됩니다. 방문자는 해당 링크에서 비밀번호를 정한 뒤 계정을 사용할 수 있습니다.

## 2. 확정 결정

### 2.1 알림 발송

**웹훅(webhook)**은 특정 URL로 HTTP 요청을 보내면 연결된 채널에 메시지가 게시되는 방식입니다.

관리자 알림은 Discord 웹훅으로 발송합니다. 사용자 초대 메일은 Supabase Auth의 내장 발송을 사용합니다.

### 2.2 승인 방식

관리자는 알림의 승인 링크를 눌러 애플리케이션의 승인 페이지로 이동합니다. 승인 페이지에서 요청자의 이메일 주소를 확인한 뒤 승인 또는 거절을 선택합니다.

### 2.3 관리자 알림 채널

관리자 알림은 Discord 웹훅으로 보냅니다. 수신 대상은 웹훅 URL이 가리키는 채널 하나이며,
URL은 프론트엔드 코드가 아니라 Edge Function 시크릿 `DISCORD_WEBHOOK_URL`에 저장합니다.

> 최초 설계는 Resend 이메일 발송이었습니다. Resend는 발신 도메인 인증(DNS 레코드 추가)을
> 요구하는데 Vercel 무료 배포의 `*.vercel.app`에는 레코드를 추가할 수 없어 사용할 수 없습니다.
> 교체 경위는 `docs/superpowers/specs/2026-07-24-admin-notify-discord-design.md`를 참고하십시오.

**Edge Function**은 브라우저 대신 비밀 키가 필요한 작업과 서버 측 검증을 수행하는 Supabase의 서버 함수입니다.

## 3. 전체 흐름

1. 방문자가 로그인 화면의 회원가입 요청 폼에 이메일 주소만 입력하고 제출합니다.
2. `signup-request` Edge Function이 사용량 제한을 검사합니다.
3. 이미 가입된 이메일인지, 같은 이메일의 처리 대기 요청이 있는지 확인합니다.
4. 새 요청이면 `signup_requests` 테이블에 `pending` 상태, 랜덤 토큰, 생성 시각으로부터 3일 뒤의 만료 시각을 저장합니다.
5. Discord 웹훅으로 관리자 채널에 `/admin/approve?token=...` 형식의 승인 링크를 게시합니다.
6. 관리자가 알림의 승인 링크를 눌러 애플리케이션의 승인 페이지로 이동합니다.
7. 승인 페이지가 `approve-signup` Edge Function에 토큰을 전달하여 요청 이메일과 현재 상태를 조회합니다.
8. 관리자가 요청을 승인하거나 거절합니다.
9. `approve-signup` Edge Function이 토큰의 존재 여부, 만료 여부, 요청 상태가 `pending`인지 검증합니다.
10. 승인한 경우 Supabase Auth 관리자 API의 `inviteUserByEmail`을 호출하고 요청 상태를 `approved`로 변경합니다. 거절한 경우 요청 상태를 `rejected`로 변경합니다.
11. 방문자가 Supabase 초대 메일의 링크를 눌러 비밀번호 설정 페이지로 이동합니다.
12. 방문자가 비밀번호를 정하면 계정 생성이 완료되고 로그인할 수 있습니다.

**`inviteUserByEmail`**은 지정한 이메일 주소로 가입과 비밀번호 설정에 사용할 링크를 보내는 Supabase Auth 관리자 API입니다.

## 4. 구성 요소

### 4.1 프론트엔드

- 로그인 화면의 회원가입 요청 폼: 이메일 주소만 입력받아 가입 요청을 제출합니다.
- 관리자 승인 페이지 `/admin/approve`: 요청 이메일과 상태를 보여 주고 승인 또는 거절을 처리합니다.
- 비밀번호 설정 페이지: Supabase 초대 링크가 연결되는 화면이며 사용자의 새 비밀번호를 설정합니다.

### 4.2 Edge Function

- `signup-request`: 가입 요청 접수, 사용량 제한 검사, 중복 검사, 관리자 알림 발송을 담당합니다.
- `approve-signup`: `GET` 요청으로 가입 요청 정보를 조회하고, `POST` 요청으로 승인 또는 거절과 사용자 초대를 처리합니다.

### 4.3 데이터베이스

`signup_requests` 테이블은 가입 요청 이메일, 승인 토큰, 처리 상태, 생성 시각, 만료 시각을 저장합니다.

### 4.4 알림과 시크릿

- `DISCORD_WEBHOOK_URL`은 관리자 알림을 받을 Discord 채널의 웹훅 주소입니다.
  이 URL 자체가 인증 수단이므로 비밀 값으로 취급합니다.
- 승인된 사용자에게 보내는 초대 메일은 Supabase Auth의 `inviteUserByEmail`이 담당하며,
  Supabase 내장 발신 주소를 사용하므로 별도 이메일 시크릿이 필요하지 않습니다.

시크릿은 Edge Function 시크릿으로 관리하며 브라우저에 전달하지 않습니다.

## 5. 데이터 모델

### 5.1 `signup_requests`

| 필드         | 형식 및 제약                                        | 설명                                      |
| ------------ | --------------------------------------------------- | ----------------------------------------- |
| `id`         | `uuid`, 기본 키                                     | 가입 요청을 식별하는 값입니다.            |
| `email`      | 이메일 주소                                         | 가입을 요청한 방문자의 이메일 주소입니다. |
| `token`      | 중복 불가                                           | 관리자 승인에 사용하는 랜덤 토큰입니다.   |
| `status`     | `pending`, `approved`, `rejected`; 기본값 `pending` | 요청의 현재 처리 상태입니다.              |
| `created_at` | `timestamptz`                                       | 요청이 생성된 시각입니다.                 |
| `expires_at` | `timestamptz`, `created_at`으로부터 3일 뒤          | 승인 토큰이 만료되는 시각입니다.          |

`timestamptz`는 시간대 정보를 고려하여 특정 시점을 저장하는 PostgreSQL 날짜·시간 형식입니다.

구독 상태와 사용량 제한 데이터는 이 테이블에 추가하지 않습니다. 이 기능에는 구독 상태 테이블이 필요하지 않으며, 기존 서비스의 일반 API 사용량은 별도 `api_usage` 테이블로 유지합니다. 가입 요청의 IP·이메일 제한은 확정된 설계에 따라 `signup_requests`의 최근 요청 수를 세어 처리합니다.

데이터 모델을 구현하기 전에는 이메일과 같은 민감 데이터와 사용량 데이터가 한 테이블에 혼재하는 것이 적절한지 사람이 직접 다시 판단해야 합니다.

## 6. 서버 동작

### 6.1 `signup-request` Edge Function

`signup-request`는 다음 순서로 동작합니다.

1. 요청에서 이메일 주소와 IP를 확인합니다.
2. 같은 IP와 같은 이메일의 최근 요청 수를 각각 검사하여 제한을 적용합니다.
3. 이미 가입된 이메일인지 확인합니다.
4. 같은 이메일로 상태가 `pending`인 요청이 있는지 확인합니다.
5. 기존 대기 요청이 있으면 새 행을 만들거나 관리자 알림을 다시 보내지 않고 "이미 요청됨" 응답을 반환합니다.
6. 새 요청이면 암호학적으로 안전한 랜덤 32바이트 토큰을 생성합니다.
7. `signup_requests`에 이메일, 토큰, `pending` 상태, 생성 시각, 3일 뒤의 만료 시각을 저장합니다.
8. `DISCORD_WEBHOOK_URL` 채널로 승인 링크가 포함된 관리자 알림을 발송합니다.
9. 방문자에게 요청 접수 결과를 반환합니다.

**Rate limit**은 일정 시간 동안 같은 주체가 보낼 수 있는 요청 수를 제한하여 스팸과 과도한 비용을 방지하는 방식입니다.

가입 요청 제한은 프론트엔드가 아니라 Edge Function에서 적용합니다. 사용자 계정이 아직 없는 단계이므로 확정된 설계에 따라 IP와 이메일을 함께 기준으로 사용합니다. 한 가지 값만 바꾸어 제한을 쉽게 우회하지 못하도록 두 기준을 모두 검사합니다.

구현 시 사용량 제한 코드에는 다음 취지의 주석을 명시합니다.

```text
요금폭탄 주의: 스팸 요청이 DB 행 적재와 승인 후 초대 메일 발송으로 직결됨
```

### 6.2 `approve-signup` Edge Function

`approve-signup`의 `GET` 요청은 다음 순서로 동작합니다.

1. URL에서 토큰을 읽습니다.
2. 토큰과 일치하는 가입 요청이 있는지 확인합니다.
3. 현재 시각이 `expires_at` 이전인지 확인합니다.
4. 요청 상태를 확인합니다.
5. 요청 이메일과 상태를 승인 페이지에 반환합니다.

`POST` 요청은 다음 순서로 동작합니다.

1. 토큰과 승인 또는 거절 결정을 입력받습니다.
2. 토큰이 유효하고 만료되지 않았으며 요청 상태가 `pending`인지 다시 검증합니다.
3. 승인인 경우 이미 존재하는 사용자인지 확인하여 중복 초대를 막습니다.
4. 기존 사용자라면 해당 사실을 관리자에게 표시하고 초대 메일을 보내지 않습니다.
5. 신규 사용자라면 `admin.inviteUserByEmail(email, { redirectTo: 비밀번호 설정 페이지 })`을 호출합니다.
6. 승인이 완료되면 요청 상태를 `approved`로 변경합니다.
7. 거절인 경우 초대 API를 호출하지 않고 요청 상태를 `rejected`로 변경합니다.

토큰은 승인 또는 거절로 상태가 변경된 뒤 재사용할 수 없습니다. 만료된 토큰과 존재하지 않는 토큰도 승인이나 거절에 사용할 수 없습니다.

## 7. 프론트엔드 동작

### 7.1 로그인 화면

로그인 화면에 이메일 주소만 입력하는 "회원가입 요청" 폼을 추가합니다. 제출하면 `signup-request` Edge Function을 호출합니다. 요청이 접수되면 "승인되면 메일로 안내됩니다"라는 안내를 표시합니다.

### 7.2 관리자 승인 페이지

`/admin/approve` 페이지는 URL의 `token` 값을 사용하여 `approve-signup`의 `GET` 요청을 호출합니다. 유효한 요청이면 이메일 주소와 현재 상태를 표시하고 `[승인]`, `[거절]` 버튼을 제공합니다.

관리자가 버튼을 선택하면 같은 Edge Function에 `POST` 요청을 보냅니다. 처리 결과에 따라 승인 완료, 거절 완료, 이미 가입된 사용자, 만료되거나 유효하지 않은 요청 등의 상태를 관리자에게 표시합니다.

### 7.3 비밀번호 설정 페이지

비밀번호 설정 페이지는 Supabase 초대 메일 링크의 랜딩 페이지입니다. 방문자가 비밀번호를 입력하면 Supabase Auth의 `updateUser({ password })`를 호출합니다. 비밀번호 설정이 완료되면 로그인할 수 있다는 안내를 표시합니다.

## 8. RLS와 접근 제어

**RLS(Row Level Security)**는 데이터베이스 행마다 어떤 주체가 읽거나 쓸 수 있는지를 제한하는 PostgreSQL 보안 기능입니다.

`signup_requests` 테이블은 RLS를 활성화하고 `service_role`만 접근할 수 있도록 합니다. 방문자와 관리자는 브라우저에서 이 테이블을 직접 읽거나 쓰지 않으며, 모든 작업은 Edge Function을 거칩니다.

**`service_role`**은 RLS를 우회할 수 있는 Supabase 서버 전용 권한입니다. 이 권한의 키는 Edge Function 내부에서만 사용하고 프론트엔드에 노출하지 않습니다.

접근 정책은 기존 `api_usage` 테이블과 같은 원칙을 따릅니다.

| 접근 주체                      | 직접 읽기 | 직접 쓰기 | 허용 경로                      |
| ------------------------------ | --------- | --------- | ------------------------------ |
| 방문자 브라우저                | 불가      | 불가      | `signup-request` Edge Function |
| 관리자 브라우저                | 불가      | 불가      | `approve-signup` Edge Function |
| Edge Function의 `service_role` | 가능      | 가능      | 검증된 서버 로직 내부          |

### 8.1 RLS 우회 경로 검토

정책 작성 후에는 다음 우회 경로가 없는지 반드시 검토합니다.

- 익명 키 또는 로그인한 일반 사용자의 토큰으로 `signup_requests`를 직접 조회할 수 없어야 합니다.
- 다른 사용자의 이메일 주소나 승인 토큰 목록을 브라우저에서 얻을 수 없어야 합니다.
- 브라우저가 `service_role` 키나 Supabase 관리자 권한을 사용할 수 없어야 합니다.
- 유효한 토큰 검증 없이 요청 상태를 변경하거나 `inviteUserByEmail`을 호출할 수 없어야 합니다.
- 승인 또는 거절된 토큰과 만료된 토큰을 재사용할 수 없어야 합니다.

이 검토의 핵심 질문은 "이 정책으로 다른 사용자 데이터에 접근 가능한 우회 경로가 있는가?"입니다.

## 9. 보안 요구사항

### 9.1 비밀 키 보호

Discord 웹훅 URL과 Supabase 관리자 API 권한은 Edge Function에서만 사용합니다. `VITE_`, `NEXT_PUBLIC_`처럼 클라이언트에 노출되는 환경 변수 접두사에 비밀 값을 저장하지 않습니다. 프론트엔드가 웹훅이나 `inviteUserByEmail`을 직접 호출해서는 안 됩니다.

### 9.2 승인 토큰 보호

승인 토큰은 랜덤 32바이트로 생성하고 중복을 허용하지 않습니다. 토큰은 관리자 채널 알림으로만 전달되며, `signup_requests`를 브라우저에서 직접 조회할 수 없으므로 외부 사용자가 토큰 목록을 얻을 수 없습니다.

`approve-signup`은 토큰이 존재하고, 만료되지 않았으며, 상태가 `pending`인 경우에만 승인 또는 거절을 처리합니다. 승인 시에도 이 검증을 통과한 뒤에만 `inviteUserByEmail`을 호출합니다.

### 9.3 스팸과 비용 방어

가입 요청은 Edge Function에서 IP와 이메일 기준의 사용량 제한을 적용합니다. 프론트엔드의 버튼 비활성화만으로 요청을 제한하지 않습니다. 스팸 요청은 DB 행 적재와 승인 후 초대 메일 발송으로 이어질 수 있으므로 서버에서 제한해야 합니다.

| 상황                                             | 처리                                                                   |
| ------------------------------------------------ | ---------------------------------------------------------------------- |
| 같은 이메일의 `pending` 요청이 이미 존재함       | 새 요청과 관리자 알림을 만들지 않고 "이미 요청됨"을 반환합니다.        |
| 승인하려는 이메일의 사용자가 이미 존재함         | `inviteUserByEmail`을 호출하지 않고 해당 사실을 관리자에게 표시합니다. |
| 같은 IP 또는 이메일의 최근 요청 수가 한도를 넘음 | 가입 요청을 거부하여 이메일 폭탄을 방지합니다.                         |
| 토큰이 존재하지 않음                             | 요청 정보 조회와 승인·거절을 거부합니다.                               |
| 토큰의 `expires_at`이 지남                       | 만료된 요청으로 처리하고 승인·거절을 거부합니다.                       |
| 요청 상태가 `approved` 또는 `rejected`임         | 처리된 토큰의 재사용을 거부합니다.                                     |

## 11. 테스트와 검증

외부 서비스에 실제 알림을 보내거나 사용자를 만들지 않도록 테스트에서는 웹훅 `fetch`와 Supabase Auth 관리자 API를 모킹합니다.

**모킹(mocking)**은 테스트에서 실제 외부 서비스 대신 호출과 반환 값을 통제할 수 있는 가짜 구현을 사용하는 방식입니다.

### 11.1 `signup-request`

- 같은 IP와 이메일에 대한 사용량 제한이 동작하는지 확인합니다.
- 같은 이메일의 `pending` 요청이 있을 때 새 요청을 만들지 않는지 확인합니다.
- 새 요청을 저장한 뒤 관리자 알림 발송을 호출하는지 확인합니다.

### 11.2 `approve-signup`

- 유효한 토큰을 승인하면 `inviteUserByEmail`을 호출하는지 확인합니다.
- 만료된 토큰과 유효하지 않은 토큰을 거부하는지 확인합니다.
- 거절을 선택하면 초대 API를 호출하지 않고 상태를 `rejected`로 변경하는지 확인합니다.

### 11.3 프론트엔드

- 로그인 화면에서 이메일을 입력해 가입 요청 폼을 제출할 수 있는지 확인합니다.
- 승인 페이지가 요청 이메일과 상태를 표시하는지 확인합니다.
- 승인과 거절 버튼이 각각 올바른 `POST` 요청을 보내고 처리 결과를 표시하는지 확인합니다.

## 12. 운영 설정

다음 항목은 코드가 아니라 각 서비스의 운영 환경에서 설정합니다.

- Discord 채널에서 Incoming Webhook을 만들고 URL을 확보합니다.
- Edge Function 시크릿 `DISCORD_WEBHOOK_URL`을 설정합니다.
- Supabase Auth의 허용된 redirect URL에 비밀번호 설정 페이지 주소를 추가합니다.
- 사용자 초대 메일은 Supabase 내장 발송을 사용합니다. 발송량이 내장 한도를 넘으면
  Supabase Auth에 별도 SMTP를 설정합니다.

## 13. 구현 완료 기준

- 방문자가 로그인 화면에서 이메일 주소만으로 회원가입을 요청할 수 있습니다.
- 중복 대기 요청과 IP·이메일 기준의 과도한 요청이 서버에서 차단됩니다.
- 새 요청이 `signup_requests`에 3일 만료 토큰과 함께 저장되고 관리자에게 승인 링크가 전달됩니다.
- 관리자가 승인 페이지에서 요청 이메일을 확인하고 승인 또는 거절할 수 있습니다.
- 승인된 신규 사용자에게 비밀번호 설정 링크가 전달됩니다.
- 만료되거나 처리된 토큰은 재사용할 수 없습니다.
- `signup_requests`는 RLS가 활성화되고 `service_role` 외의 직접 접근이 차단됩니다.
- Discord 웹훅 URL과 Supabase 관리자 권한이 프론트엔드에 노출되지 않습니다.
- 테스트에서 웹훅 `fetch`와 Supabase 관리자 API를 모킹하여 핵심 성공 및 실패 흐름을 검증합니다.
